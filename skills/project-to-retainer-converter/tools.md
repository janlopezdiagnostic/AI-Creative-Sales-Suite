# Tools: Project to Retainer Converter

This skill works in two modes. Declare the mode, and what you actually saw, in every output (SKILL.md standing rule 8).

- **Connected mode:** the user's assistant has live access to a tool (CRM, Figma, Sheets, calendar) through a connector the user set up. You may read what the connection exposes. Writes follow the confirmation rule below.
- **Manual mode:** the user pastes records, exports files, or shares screenshots. You work only from what was supplied. If a fact is not in the supplied material, it is missing, not estimable.

The standing rule for every tool: read first, write only with confirmation. You never change a CRM record, a calendar, a shared file, or a sheet without the user reviewing the exact change and confirming. Drafts stay drafts until the user says write, or send.

## CRM (HubSpot, Pipedrive, or the studio's system)

What it is for here: the completed project record, the expansion log, retainer stage tracking, and the door-open record after a decline.

Connected mode:
- Read: deal and company records, past project notes, contact roles (champion, signer, payer), prior retainer conversations and their outcomes.
- Draft, for user confirmation: an expansion log entry (routes found, evidence, owner, trigger, size), a retainer stage update (recap sent, meeting held, proposal issued, decision and date), and after a decline, the verbatim reason and the dated re-entry trigger.
- Confirm before writing: every entry. Show the exact text. A decline reason recorded inaccurately poisons the future conversation it is meant to protect.

Manual mode:
- Ask for: the project record export or paste, the contact list, and any prior proposal history.
- Produce the same log entries as copy-ready text for the user to paste, and say what you could not verify from the export (for example, whether the champion still works there).

Never: log another client's terms into this client's record, record a verbal maybe as a commitment stage, or set a follow-up date the user has not agreed.

## Figma (guardianship file audits)

What it is for here: evidencing the state of the system the retainer would guard: the delivered brand or packaging files, component libraries, artwork templates, and what has drifted since handover.

Connected mode (user's Figma connector or MCP access, as set up in the suite's Figma setup guide):
- Read: file and page structure, component and variable counts, published library status, comments since handover, and version history summaries where the connection exposes them.
- Produce: a guardianship audit summary: what exists, what has been added or altered outside the system, drift instances worth citing in the recap or expansion map, each tied to the file and date you actually saw.
- You are reading design files as evidence. You do not edit them under this skill, at any confirmation level; edits belong to delivery work, not to a sales audit.

Manual mode:
- Request: exports of the library or file pages (PDF or PNG), a screenshot of the components panel, or the client's own file inventory list.
- Work from the exports and label the audit as export-based, with the export date. Drift claims are limited to what the exports show; a screenshot cannot prove a negative ("nothing else changed"), and the output must not claim it does.

## Sheets (usage tracking and retainer economics)

What it is for here: the retainer usage log (days used by role against the block), the cost-of-ad-hoc comparison, and the quarterly review pack.

Connected mode:
- Read: the studio's usage sheet or time records for the completed project and any running retainer.
- Draft, for user confirmation: a usage summary table (block, used, percentage, by role), the ad hoc comparison built from the client's own project record, and review charts data. Rates in any calculation come from the rate sheet, never typed from memory; a missing rate stops the calculation at that line and shows [TO CONFIRM].

Manual mode:
- Request the time or usage export (CSV or paste). Produce the same tables as markdown. If the export lacks role splits, say so and present totals only; do not reconstruct a role mix that the record does not contain.

## Calendar (timing)

What it is for here: the timing plan in SKILL.md Step 6: launch anniversaries, the client's planning and budget dates, reset and seasonal windows, review dates, and agreed re-entry triggers after a decline.

Connected mode:
- Read: the user's calendar for project milestones already recorded, quarterly review dates, and known client events the user has logged.
- Draft, for user confirmation: timing plan entries and review reminders. Client-side dates (their planning freeze, their reset) usually live outside your calendar; if they are not there, they come from the user's supplied information and are marked with their source.

Manual mode:
- Work from the dates in the project record and the client's supplied calendar information. Produce the timing calendar (templates/timing-calendar-template.md) as a document. Every client-side date carries its source; a date you inferred from a seasonal pattern is marked as inferred, with the pattern stated.

Mode: [Connected / Manual]. Sources seen: [list]. Not seen: [anything relevant you could not access]. Writes made: [none, or the confirmed writes, listed].
